# 记忆修剪器 (astrbot_plugin_memory_trimmer)

> **声明**：本插件的核心代码由 DeepSeek AI 辅助生成，经人工调试与整理，仅供学习交流使用。

固定人设 + 多策略上下文裁剪。通过精准的上下文管理，有效避免 AstrBot 自动压缩导致的缓存失效，稳定提升大模型的缓存命中率，极大降低 API 调用成本。适用于长对话、多图转述等容易引起上下文爆炸的场景。

---

## ✨ 功能特点

- **固定人设**：强制插入系统提示词，保证角色一致性，死守缓存命门。
- **三种清理策略**：
  - `hard`：超过指定轮数直接截断（传统方式）。
  - `progressive`：超过阈值后每次只删掉最早的一小部分（平滑遗忘）。
  - `length`：基于上下文长度（字符数）触发裁切，精准控制上下文大小，适合图片转述较多的群。
- **多模态长度估算**：精准计算文本与图片转述的字符数，防止上下文悄悄爆炸。
- **安全截断清理**：内置外科手术级清理逻辑，即便截断点卡在工具调用（Tool Calls）中间，也会自动清理孤立节点，绝不报错。
- **与原有插件完全兼容**：配置平滑，无外部网络请求，纯本地安全运行。

---

## 📦 安装方法

1. 在 `data/plugins/` 目录下新建文件夹，命名为 `astrbot_plugin_memory_trimmer`。
2. 将以下四个文件放入该文件夹：
   - `main.py`
   - `metadata.yaml`
   - `_conf_schema.json`
   - `README.md`
3. 在 AstrBot WebUI 中**重载插件**。

---

## ⚙️ 配置选项

| 配置项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `system_prompt` | text | `"你是一个 helpful assistant。"` | 系统人设提示词 |
| `clean_strategy` | select | `"hard"` | 清理策略：`hard` / `progressive` / `length` |
| `max_history_rounds` | int | `5` | 硬裁剪模式下保留的最近轮数 |
| `progressive_trigger_rounds` | int | `30` | 渐进模式触发阈值（轮数） |
| `progressive_keep_rounds` | int | `15` | 渐进模式至少保留的轮数 |
| `progressive_clean_ratio` | float | `0.3` | 渐进模式每次清理的比例 |
| `max_history_length_kb` | int | `800` | 长度模式触发阈值（KB） |
| `max_keep_length_kb` | int | `400` | 长度模式裁切后保留量（KB） |

---

## 🚀 使用建议

- **如果你主要聊天文字多、图片少**：用 `hard` 模式，配合 `max_history_rounds` 控制轮数。
- **如果你希望机器人慢慢忘记旧事，而非突然失忆**：用 `progressive` 模式。
- **如果你的群图片很多，转述内容经常撑爆上下文**：**强烈推荐 `length` 模式**，设置 800KB 触发、400KB 保留，能有效控制上下文总大小，避免缓存频繁失效。

---

## 🧠 长度裁切与安全清理原理

插件会在每次 LLM 请求前估算当前上下文的字符数（中英文混合，1 字符 ≈ 0.5~1 token）。若超过 `max_history_length_kb`，则从最早的非 system 消息开始删除，直到剩余长度低于 `max_keep_length_kb`。

**安全清理**：截断发生后，如果发现开头是孤立的 `tool` 消息，或结尾是缺失结果的 `assistant` 工具调用请求，插件会自动将其剔除，确保发给 API 的上下文结构合法。

## 💡 设计考量与答疑 (FAQ)

**Q1：为什么需要这个插件？AstrBot 自带的上下文压缩不行吗？**
A1：AstrBot 自带的自动压缩机制，通常会直接截断或重写整个历史记录。一旦前缀发生变化，大模型的**整个缓存将全部失效**，导致下一次对话产生高昂的全价 API 费用。本插件通过“外科手术式”的精准裁剪，最大化保留未变动的前缀，从而死守缓存命中率。

**Q2：为什么插件要强制覆盖 / 替换 System Prompt？**
A2：部分 AstrBot 的默认人格或动态提示词插件，会在每轮对话中向 System Prompt 注入“当前时间”、“好感度”等动态变量。这会导致每次请求的上下文第一句话都不一样，直接宣告缓存失效。本插件**强制锁定** System Prompt，放弃动态变量，以换取极致的缓存稳定性。

**Q3：既然锁定了 System Prompt，会不会和 AstrBot 原生的人格设定冲突？**
A3：会覆盖原生设定。因此，请务必将你想要的完整人设、规则、语气，直接写进本插件配置项的 `system_prompt` 中。

**Q4：截断上下文会导致 Tool Calls (工具调用) 报错吗？**
A4：不会。这是本插件 v2.3.0 的重大升级。如果在使用带有联网搜索、代码执行等工具的插件时，截断点刚好卡在 `assistant(tool_calls)` 和 `tool(返回结果)` 之间，API 会直接报 400 错误。本插件内置了**安全清理机制**，会自动清除孤立的 `tool` 节点，确保发给 API 的上下文结构 100% 合法。

**Q5：长度裁切用 KB 估算，如果模型支持 1M 上下文，可以设大一点吗？**
A5：完全可以。默认的 800KB 触发、400KB 保留是为了兼顾大部分 64k/128k 模型的用户。如果你使用的是支持 1M (100万) Token 上下文的模型（如 DeepSeek V4.1-Flash），你完全可以把触发阈值设到 2000KB，保留量设到 1000KB，尽享超大杯上下文。

**Q6：配合好感度、动态状态等需要注入上下文的插件时，效果如何？**
A6：这是一个**双刃剑**。虽然本插件锁死了 System Prompt，但如果**其他插件**在运行过程中，强行往 `req.contexts`（历史消息）或 System Prompt 中动态插入了变化的内容（比如实时好感度、当前状态、时间戳等），依然会破坏上下文的前缀，导致缓存失效。因此，你会发现输入 Token 的消耗“一时大一时小”。如果你追求极致的缓存命中率与省钱，建议关闭或禁用其他会在对话中动态注入内容的插件；如果你更看重角色互动的丰富度，则需要接受一定的缓存折损。本插件无法越权控制其他插件的注入行为，请知悉。

---

## 📌 注意事项

- 长度裁切使用字符数估算，并非精确 token 数，但误差在可接受范围内。
- 裁切操作会改变上下文前缀，导致缓存失效，但触发频率远低于 AstrBot 自动压缩，总体成本更优。
- 本插件完全在本地运行，仅对发送给 LLM 的上下文进行裁切，不涉及任何数据外传，无风控风险。
